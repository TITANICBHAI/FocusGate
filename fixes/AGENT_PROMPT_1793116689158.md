## 3. Operating rules (mandatory — mirrored in `plan.md` and `fixes/TRACKER.md`)

1. **Authorization gate.** The plan is the implementation contract, not authorization by itself. Do not begin app-code implementation until the owner explicitly authorizes it. If the requested scope or authorization is unclear, stop before changing app code and ask.
2. **Work alone.** Do not create, invoke, or delegate to sub-agents.
3. **Follow the plan's implementation order and the tracker.** Do not silently widen scope or change the plan's contract.
4. **Inspect before editing.** Before editing, inspect the relevant current code, project instructions, and the working tree. Preserve unrelated user changes and user data.
5. **Respect the plan's no-touch list** unless the owner explicitly changes the scope: do not hand-edit `dist/` (plan §2.11); do not blindly recreate files missing from the upload (plan §1.2 — check the GitHub repo first); do not port the "Do not port" features (plan §6 WP7), including the Discord crash/feedback webhook and any telemetry.
6. **Destructive actions.** Treat task replacement and any other deletion of user data as destructive. Keep replacement disabled by default, preserve explicit confirmation and required safety guards, and do not perform destructive actions without the owner's authorization.
7. **Testing environment.** Run Gradle or Android tests on Replit using the current workflow or scripts under `scripts/`. For this repo the equivalent checks are the npm scripts (`npm run typecheck`, `npm test`, `npm run build`) run the same way. Test only the production flavor — the flavors are fundamentally the same thing, so running the same test in both flavors equals the same results. Do not build APKs on Replit, and keep APK building out of Gradle/Android test runs. If verification is needed, use GitHub Actions only when the owner explicitly requests APK-building verification; otherwise state clearly that those checks were not run.
8. **GitHub.** Do not push to GitHub or start, poll, or monitor GitHub Actions unless the owner explicitly asks.
9. **Secrets.** Do not expose, copy into files, or print secrets or credentials.
10. **Test style.** Use behavior tests with fake clocks and event sources. Do not add tests that read Kotlin source files as text. Logic under test must not call the system wall clock directly.
11. **Tracker discipline.** Follow the tracker rules at the top of `fixes/TRACKER.md` at all times (summarized in §4 below).

## 4. Tracker discipline (summary — full rules at the top of `fixes/TRACKER.md`)

1. At the start of a phase, set it to IN PROGRESS and record a dated start note in its notes **before** doing its work.
2. After each meaningful change, update the relevant phase notes, status, progress, evidence, and history — do not wait until the phase is complete.
3. As soon as any checklist item or individual verification step (each test, lint, or build check) completes or fails, update its checkbox/status and record the exact command and observed result in `fixes/TRACKER.md` **before** starting the next item or check.
4. Tick a checkbox only after its work is complete **and verified**. Never mark attempted, partial, or unverified work complete.
5. For every completed item, record changed files, the exact verification performed, and its observed result.
6. If a check fails, leave the item unchecked, record the observed failure, preserve it, and append the fix and successful rerun when available.
7. Record decisions, blockers, and deferred work. Never erase old evidence or failure history.
8. Before finishing, reconcile `fixes/TRACKER.md` with the actual code and test evidence; leave incomplete items unchecked and explain why.

## 5. Working method once authorized

- Work **exactly one WP at a time, in plan order**: WP0 → WP1 → WP1b → WP2 → WP3 → WP4 → WP5 → WP6 → WP7 (Tier A → Tier B) → WP8 → WP9 → WP10. WP1b spikes come before WP2/WP3. Do not start WP7 before milestone **M1 (WP0–WP3) is green**.
- Per WP: dated IN-PROGRESS note → tasks → verification → evidence in `fixes/TRACKER.md` → tick verified boxes only → then move on.
- Commit once per WP (or per sub-task for WP2/WP3); never mix refactors and behaviour changes in one commit (plan §0.4).
- When a decision is unclear, use the default listed in plan §10 and note it in the commit message and the tracker; do not stop to ask unless a default is missing — except for anything that requires explicit authorization under the rules above.
- A WP is done only when **every** of its acceptance criteria passes (plan §0.2). A finding tagged **Verify** must be reproduced first (repro steps in plan §4.6) before fixing.

## 6. Explicitly out of scope without the owner

- Pushing to GitHub; starting, polling, or monitoring GitHub Actions; APK builds — except when the owner explicitly requests APK-building verification via Actions.
- Any destructive action: deleting user data, "replace"-style imports, storage resets, task replacement — even if the plan describes a guarded path, get explicit authorization first.
- Porting anything on the plan's "Do not port" list, adding network calls, analytics, or remote code (plan §2 ground rule 1).
- Recreating the files missing from the upload (`LICENSE`, `STORE_LISTING.md`, `docs/`, workflows) without the WP0 GitHub check first.
